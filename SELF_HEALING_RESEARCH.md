# Recovery verification and self-healing research

## Product direction

The useful progression is **detect → preserve evidence → propose a scoped action → obtain approval → execute → verify → escalate or roll back**. A component inventory supplies context; it does not close this loop. The first implementation below adds the verification boundary and fixes the application's own worker cleanup. It does not claim autonomous PC repair.

## Research and implications

1. [Huang et al., Panorama, OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/huang): failure detectors can miss problems seen by a component's callers. Product implication: combine passive telemetry with bounded application-level health contracts in a future stage, such as successful storage read/write or service response, rather than equating process existence with health. We do not reproduce Panorama's distributed instrumentation or its benchmark results.
2. [Li et al., Can We Trust Auto-Mitigation?, ISSRE 2024](https://www.microsoft.com/en-us/research/uploads/prod/2024/08/ISSRE24_UPLearning.pdf): intervention changes subsequent observations and can make original failure labels uncertain. Product implication: preserve the pre-action evidence, label actions as user reports, and avoid claiming that an alert disappearing proves the original prediction or repair. No predictive model from this paper is implemented here.
3. [Gray Failure, SREcon 2024](https://www.usenix.org/conference/srecon24americas/presentation/li): differential observability is an operational problem across components. Product implication: explicitly retain lost/unreadable sources as evidence gaps instead of recovered components.

## Implemented in this change

### Recovery verification

Open Reliability, run a check, and choose **Capture fault baseline** when warning or critical evidence exists. The main process captures the original snapshot; the renderer cannot supply a fabricated baseline through this API. The baseline includes all current warning/critical signals and persists separately from the rolling monitoring history.

Review recommended actions, perform an approved action, then record one action and the workload to repeat. PC Health runs no repair command. The action timestamp is generated by the main process and cannot be edited through the API. Capture another baseline for another intervention.

Verification requires three consecutive comparable follow-ups spanning at least two minutes. It refuses a stable verdict for missing, unreadable, stale or changed target sources, changed rule/platform identities, counter resets, increased error counters, unresolved non-counter warnings, or new critical findings. The latest follow-up must be no older than 15 minutes. Stable lifetime error counters can support “no new errors observed”; they cannot establish a repaired component. Reboot-sensitive counter identities deliberately become incomparable after restart.

The two-minute / three-check policy is an explicit engineering starting point, not a statistically validated assurance interval. Checks are observations, not controlled causal experiments. A stable result says only what the observed sources support. Repeat the original workload and extend monitoring for intermittent faults. Verification uses retained follow-up history; if it is unavailable, the result becomes inconclusive or awaits evidence rather than assuming success.

Storage is local, bounded to 20 verification cases / 16 MiB, with validated reads, serialized atomic writes, explicit deletion and preservation of unreadable files. Notes and baseline measurements can contain user-entered or device-identifying data. Existing monitoring exports do not include these separate verification records yet.

### Worker lifecycle correction

The former watchdog scheduled an unreferenced kill timer and rejected immediately. A short-lived caller or test runner could exit before cleanup, leaving a diagnostic process running. The watchdog now settles only after its child exits and cleans its owned POSIX process group. On Windows it terminates the worker; a full Windows Job Object implementation for descendant containment remains future work. The next user-requested check starts a fresh worker. No OS service restart or repair authorization is implied.

Fault tests verify actual process termination rather than only checking a rejected promise. Recovery tests cover sustained observations, missing sources, resets, stale evidence, duplicate snapshots, regressions, action immutability and persistence. UI tests use explicitly synthetic fixtures in disposable profiles; those fixtures never appear in the user's real history.

## Next implementation stages

1. **Application-level health contracts:** explicitly opt-in scratch-file write/flush/readback and selected local-service response probes, each isolated with deadlines and disk quotas. These improve observability without pretending to certify all storage media or physical RAM.
2. **Approved recovery adapters:** support individually reviewed service restarts with exact service identities, a displayed impact statement, configuration snapshot, cooldown, and post-action contract checks. Never execute free-form model-generated shell commands. Platform-native privilege and service semantics need separate qualification.
3. **Rollback and circuit breakers:** limit attempts, stop on a new critical finding, preserve a timeline, and escalate when observation becomes incomplete. Configuration rollback is distinct from reversing a service restart or restoring lost in-memory work.
4. **Controlled fault evaluation:** use disposable services and virtual machines to measure false recovery, missed faults and recovery latency before enabling unattended execution. Build labeled failure/recovery data before adding an offline inference model.

The distinctive product opportunity is a local, auditable recovery loop with measurable postconditions. More sensor tiles or an LLM-generated explanation alone do not provide that capability.
