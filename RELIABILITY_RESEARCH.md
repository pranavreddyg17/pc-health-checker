# PC Health: research and reliability architecture

September 16, 2026 · implementation increment 0.5.0 · research-informed engineering, not a validated failure-prediction model

The product direction is a local reliability assistant: detect observable degradation, preserve evidence, distinguish hardware faults from operational problems, and help a person choose and verify an intervention. For a server, the most useful output may be “protect data and inspect the storage path,” rather than “buy an SSD.” For an ordinary laptop, it may be “this source is unavailable; use the OEM diagnostic before replacing anything.”

The user confirmed **opt-in local monitoring and alerts; repairs require approval**. Processing remains local and offline. This supersedes the original manual-only scope. No autonomous repair executor, privileged helper, cloud model, fleet service, or persistent OS daemon has been installed by this increment.

## What the research changes

These papers concern particular populations and environments. Their observations motivate the design; their historical failure rates are not transferred to an individual modern device. None supplies a universal wear percentage for CPU, RAM, GPU, motherboard, fan or power supply.

Further papers sharpen the requirements for degraded performance and GPU clusters:

- Gunawi et al., **Fail-Slow at Scale**, FAST 2018, documents hardware performance faults across storage, processors, memory and networking. A device can remain functional while degrading a workload. **Design implication:** correlate reliability events with matched workload measurements; high utilization alone is insufficient. [Paper](https://www.usenix.org/conference/fast18/presentation/gunawi)
- Xiong et al., **SuperBench**, ATC 2024, uses proactive validation to uncover hidden degradation in AI infrastructure. **Design implication:** an eventual opt-in validation suite needs hardware-specific baselines and an explicit workload budget. Its published results do not establish accuracy or safety for this app's passive checks. [Paper](https://www.usenix.org/conference/atc24/presentation/xiong)
- Yao et al., **Holmes**, NSDI 2025, localizes irregular training iterations using communication-operator evidence and cross-iteration analysis. **Design implication:** GPU health for distributed training needs application and communication context beyond nvidia-smi. This app currently reads management counters; it does not reproduce Holmes. [Paper](https://www.usenix.org/conference/nsdi25/presentation/yao)

The product's distinguishing value should be **evidence → change detection → prioritized investigation → approved intervention → verified outcome**. The current increment implements the observation and alert portion of that loop. The repair workbench retains human-entered actions and results; it is not yet automatically linked to reliability incidents.

## Implemented checks and their exact boundaries

All probes are passive. Optional management tools must already exist and be readable. There is no automatic installation, elevation, filesystem repair, disk self-test, restart, firmware update, memory offlining, workload eviction or device reset.

| Area                | Implemented in 0.5                                                                                                                                            | Important boundary                                                                                                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ATA drives          | Recognized ID **and name** pairs for pending, offline-uncorrectable, reallocated and interface CRC counts through existing smartctl collection on macOS/Linux | Vendor attribute semantics vary. Unrecognized attributes and proprietary wear indicators remain uninterpreted. SMART uses standby-aware reads and may be inaccessible behind controllers.          |
| NVMe                | Existing status, warning, endurance and media-error evidence; available spare compared with the device's reported threshold                                   | No guaranteed failure forecast. SMART status can miss faults. Windows raw NVMe logs remain unimplemented.                                                                                          |
| Windows disks       | OS health plus available uncorrected read/write counts                                                                                                        | Null or unrepresentable counts stay unknown. Generic health cannot isolate media, firmware or controller causes.                                                                                   |
| Linux ECC           | EDAC memory-controller corrected/uncorrected counts with boot epoch and available driver-reset metadata                                                       | No slot-level replacement claim; EDAC may be absent on non-ECC, unsupported or inaccessible hardware. A privileged RAS/event adapter is future work.                                               |
| Linux cooling/power | hwmon temperatures against driver critical thresholds; available critical, fan, voltage and power alarms; sensor fault indication                             | Missing limits stay unassessed. Zero RPM alone is not a failed fan. No universal temperature cutoff or inferred PSU wear. BMC/Redfish is not implemented.                                          |
| NVIDIA GPU          | Optional nvidia-smi volatile ECC counts, pending page retirement and retired double-bit pages                                                                 | Capability varies by GPU/driver. ## Architecture in this increment

```text
Desktop UI                         Node headless CLI
    | narrow IPC                       | fixed arguments
    +---------- ReliabilityService ----+
                    | one collection at a time
                    v
             disposable worker
                    | fixed commands / bounded reads
          +---------+----------+
       OS adapters          optional vendor tools
          +---------+----------+
                    v
      validated observations + explicit coverage gaps
                    |
      comparable counter changes + versioned rules
                    |
       atomic local history + deduplicated alerts
                    |
       UI / optional desktop notification / JSON output
```

- A signal contains source, scope, collection time, measurements, severity, explanation, next action and limitations. “Within checked limits” applies only to that check; unavailable information is visible.
- Counter comparison requires the same identity, source, platform, rule version and reset epoch, an increasing timestamp and a gap no longer than 24 hours. Decreasing counters or driver-reset evidence invalidate a delta. Unidentified drives never receive cross-observation counter deltas.
- Linux boot IDs and available EDAC reset metadata constrain comparisons. Other volatile counters deliberately start a new baseline when the collector process session changes. Not every driver reload can be detected; a reset followed by a larger counter may escape detection where reset metadata is absent.
- A missing formerly readable source is carried forward as unavailable, including on later observations. It cannot silently look repaired. A moved/replaced device may require interpretation; this preview has no asset topology editor.
- First warnings/critical findings and severity transitions create alerts. Repeated unchanged findings update their observation count. Increasing counters can notify again after 30 minutes. Source loss creates a coverage alert. This simple policy needs fleet-scale alert-volume evaluation; historical nonzero counts can be noisy.
- Acknowledgment records review, not recovery. Restored checks appear in subsequent observations; there is no verified incident-resolution state machine yet.
- Monitoring is explicitly enabled at 60/300/900-second intervals measured after the prior check completes. Default is off, including after restart. No overlap with hardware scanning/performance recording. Suspend pauses collection; wake schedules the next check if monitoring remains enabled. Closing the window stops desktop monitoring.
- Worker collection has a parent deadline of 30 seconds; inner probe deadlines are 20 seconds and command deadlines 15 seconds. Cancellation is cooperative, followed by forced worker termination. POSIX uses a private process group to terminate its diagnostic descendants. Windows descendant cleanup still needs a Job Object implementation and real-host qualification; the watchdog must not be described as a production Windows process-tree supervisor.
- Validated history retains up to 120 snapshots and 200 alerts, bounded by 32 MiB with earlier snapshot pruning. Atomic replacement, exclusive write locks and revision checks prevent stale writers overwriting newer evidence. Malformed data is preserved and collection stops. An abrupt crash may leave a lock; verify the writer is stopped before removing a stale lock.
- No automatic OS action is performed. Notifications go only through the local OS after opt-in; delivery depends on notification permissions/settings. There is no email, webhook, cloud upload or remotely reachable API.

### Headless operation

After `npm run build`:

```sh
node dist-electron/health-cli.cjs --once --data-dir /path/to/dedicated/local/state
node dist-electron/health-cli.cjs --watch --interval 300 --data-dir /path/to/dedicated/local/state
```

Deploy the entire `dist-electron` directory so the worker is present. Node.js 22.12+ is required; the CLI does not import Electron or need a display server. The default state directory is `~/.pchealth-reliability`. Use one dedicated local directory per host/process; do not point the CLI at the desktop profile or a shared network filesystem. `probe.lock` prevents two CLI processes using the same directory concurrently. No service manager unit is installed.

`--once` emits one snapshot and exits: **0** all returned checks within limits; **1** at least one warning; **2** at least one critical finding; **3** incomplete coverage without a warning/critical finding; **4** collection/storage/argument error. Priority is critical, warning, incomplete, clear. Consumers must still inspect coverage on exits 1/2; absence of warnings is not complete hardware validation. Unsupported capabilities commonly produce exit 3.

`--watch` emits newline-delimited `snapshot` and `alert` records, writes collection warnings to stderr, and stops on SIGINT/SIGTERM. Three consecutive collection/storage failures stop monitoring with exit 4. Normal shutdown exits 0; an operator is responsible for supervision. JSON contains local signal keys, device/service labels and paths. Unlike the previewed desktop export, CLI output is raw local evidence; protect access before integrating it into another system.

## The next work that creates deeper practical value

These are requirements and acceptance gates, **not completed features**. Order them by evidence and recoverability rather than adding more dashboard gauges.

1. **Hardware error attribution and topology.** Decode WHEA/CPER severity and device fields; Linux RAS/EDAC DIMM labels, PCIe AER and reset events; controller → device → pool → volume relationships; NVIDIA Xid/row remapping; AMD RAS. Correlate by time and device without declaring causality from coincidence. Acceptance: captured vendor fixtures, malformed inputs, duplicate-event handling, stable replacement identities and field validation on known hardware.
2. **Data preservation and integrity.** Read backup recency from supported local providers, independently track restore-test evidence, ZFS scrub outcomes/checksum errors and filesystem error events. An existing backup job is not a tested restore. User-selected integrity manifests require a budget and access controls; they must not scan arbitrary personal files by default. Acceptance: stale/inaccessible backup, corrupted restore fixture and hidden RAID members all produce explicit uncertainty.
3. **Application and workload health.** User-defined expected service state and allowlisted local health endpoints; dependency maps and restart-loop detection; performance evidence linked to reliability incidents. Acceptance: distinguish intentional downtime, resource starvation, network dependency failure and process death. No remote credentials or arbitrary URLs become renderer-controlled commands.
4. **Maintenance plans with approval.** Each proposed action contains the specific target, evidence snapshot, preconditions, downtime/blast radius, exact allowlisted operation, rollback if possible, success measurement and expiration. Approval must authorize that concrete plan. Re-read evidence at execution to avoid acting on stale conditions. Acceptance: target changed, evidence vanished, redundant member failed, approval expired or verification timed out all prevent/stop the action.
5. **Bounded recovery executor.** Begin only with explicitly allowlisted, reversible service operations in a lab. Enforce a single attempt, cooldown, transaction journal, emergency stop and independent verification. Never let a language model emit privileged shell commands. Disk/RAID repair, thermal limits, firmware, reboot and memory offlining require distinct policies and representative test environments. A component can be isolated or a workload moved; worn silicon cannot be repaired by software.
6. **Local AI investigator.** An optional offline model may explain evidence, rank hypotheses and draft structured plans. Deterministic validation and approval remain outside the model. Treat logs and device names as untrusted data. Measure unsupported diagnoses and unsafe proposals, not only eloquence. No model or inference runtime is included in 0.5.
7. **Datacenter control plane.** Add authenticated host identity, retention/storage designed for long histories, inventory/topology, rack/power fault domains, workload draining, maintenance windows, audit access and an out-of-band BMC path. A local agent cannot notify when its OS or power is completely gone; an independent heartbeat receiver/watchdog is required. Air-gapped/on-prem deployment can retain the local-data requirement, but needs a deliberate network scope decision.

## Validation and release gates

Current development validation covers parsers and rules, reset-aware comparisons, unknown-data handling, missing-source retention, alert deduplication, corrupt history preservation, bounded retention, stale writers, monitor enable/stop/suspend, failure circuit breaking and worker deadlines. Desktop integration exercises real macOS observations, history/restart, opt-in monitoring, acknowledgment, export and accessibility. The Node path exercises collection, lock exclusion and graceful watch shutdown.

**Qualification boundary:** this development host is macOS on Apple silicon. Linux and Windows adapters have synthetic parser fixtures; that is not real-device certification. No ECC server, RAID failure, NVIDIA datacenter GPU, Windows descendant watchdog or actual notification delivery has been qualified here. Some OS/build/driver combinations will expose less than the matrix above. Production admission must require:

- A declared OS/version/architecture/hardware/driver matrix, including containers and guests with hidden physical hardware.
- Real known-good and already-faulty hardware or captured traces; no intentional hardware damage. Label time, repair outcome and source provenance.
- Fault replay for permissions loss, malformed output, reboot/reset, hot removal, storage-full, collector hang, corrupt history and concurrent writers.
- Measured collection CPU, memory, disk writes, power impact, p95 latency and notification volume. A one-minute interval is available, not an overhead guarantee.
- Detection precision/recall by fault class, false alerts per host-day, coverage and time-to-detection. “Healthy” fixtures alone cannot validate a predictor.
- Chronological and model-family-held-out evaluation for any learned failure model, with calibration, censored observations and maintenance-label bias accounted for.
- For future repair agents: successful symptom verification, unnecessary actions, data loss, availability impact, rollback success and escalation quality under injected faults. AIOps-style benchmarks are a starting point, not production authorization.
- Signed distribution, supported-runtime policy, privacy review, uninstall/data-retention behavior, supervision and recovery documentation.

The valuable claim today is that PC Health **collects and explains more relevant reliability evidence and can track it locally over time**. “Preserves any PC,” “predicts every component failure” and “self-heals a datacenter” would be unsupported claims.
